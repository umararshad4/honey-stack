# Prepared QA speed comparison — 2026-11-01

The optimized e2e + native WebMCP workflow completed this prepared 24-case fixture faster than the older QA script. This is a workflow measurement, not an equal-resource engine benchmark or a first-time agent benchmark.

| Workflow | Workers | Median wall time | Range | Runs | Known defect groups | Unexpected outcomes |
|---|---:|---:|---:|---:|---:|---:|
| Older QA | 1 | 14.222s | 14.152–14.410s | 5 | 6/6 | 0 |
| Optimized e2e only | 4 | 13.211s | 12.921–13.284s | 5 | 6/6 | 0 |
| Optimized e2e + WebMCP | 4 | 12.856s | 12.738–13.245s | 5 | 6/6 | 0 |

WebMCP workflow used **9.61% less median wall time** than older QA. All 15 measured executions contained 24 cases: 11 expected passes and 13 expected failures. The deliberately broken fixture should exit 1. No case was skipped or blocked. All 195 failing-case results retained a valid PNG. WebMCP runs each recorded six successful native `create_task` calls; the other workflows made zero WebMCP calls.

## What changed

- Read the upstream browser, configuration, runner, debugging and scheduling implementation docs before changing the workflow.
- Split independent cases across four coherent flow files, with four workers and fresh contexts. The older script stays serial. This consumes more concurrency and is an explicit part of the gain.
- Disable full tracing for this audit, while checking the required failure screenshots and observations still exist. Existing older QA did not collect full traces either.
- Remove duplicate polling of values already read after completion. The local fixture handles these mutations synchronously; reload assertions run after load and page readiness. Async applications still require their real completion signal.
- Preserve actual UI actions for form creation, search, checkboxes, Escape, validation and layout. WebMCP replaces only the fixture creation in persistence/search setup.
- Capture large trees and row dumps on failure instead of every successful action.
- Shorten the main QA skill and route to focused references; use native reports for ordinary QA. This reading-time improvement was not measured here.

## Method and limits

- Same local synthetic Task desk fixture, Chromium 156.0.8078.4, Node 24.18.0, e2e 0.22.0, web engine 0.15.4 and playwright-core 1.64.1. Dependencies were preinstalled.
- Twelve behaviors at desktop 1440×900 and mobile 390×844. Both runners use 1000ms assertion waits and 2000ms action bounds where applicable; the original scripts retain their navigation handling. Test text differs between implementations but exercises the same Unicode input class and case contract.
- Wall time starts before isolated browser launch and ends after command cleanup, including runner/report generation. Artifact copying by the measurement harness is outside the timer. AI reading, writing, installation and app-server startup are excluded.
- One excluded warm-up, then five runs per workflow. Older and WebMCP alternate order; e2e-only runs afterward as a control, so small differences between e2e and WebMCP need stronger randomized trials before attributing them to the API.
- All runs were sequential at the command level. Only independent cases inside the optimized runner execute concurrently.
- This failure-heavy fixture is useful for regression parity. It does not establish the same speedup on a healthy production app or prove lower first-time agent QA duration. No guaranteed speedup or universal WebMCP advantage is claimed.
- The earlier cold-agent numbers (75.6s / 127.5s / 123.9s) measure a different boundary and are not comparable to this table. They have not been remeasured by this experiment.
