# Third QA speed improvement — 2026-11-01

The same 24-case fixture was run again after the browser-path and launcher changes below. These are prepared-command measurements. The faster browser path is shared by every row except the v2 flow, so older QA and e2e-only are not handicapped by the old launcher.

| Workflow | Browser path | Workers | Median | Range | CPU per run | Qualified runs | False alarms |
|---|---|---:|---:|---:|---:|---:|---:|
| Older QA | new shared path | 1 | 7.209s | 7.142–7.381s | 5.8s | 5/5 | 0 |
| e2e only | new shared path | 4 | 4.997s | 4.929–5.705s | 16.5s | 5/5 | 0 |
| e2e + WebMCP, v2 flow | v2 launcher | 4 | 11.215s | 10.607–12.469s | 33.9s | 5/5 | 0 |
| **e2e + WebMCP, v3 flow** | shipped launcher | 4 | **3.396s** | 3.105–3.555s | 14.5s | 5/5 | 0 |

The v3 WebMCP flow used **69.7% less median wall time than the v2 flow** measured in the same rotation (**3.30× faster**) and 57% less CPU. It used 52.9% less than older QA (2.12×) and 32.0% less than e2e only (1.47×), with both of those on the same faster browser path. On the old launcher, older QA took 13.6–14.9s in a two-run pilot.

All **30/30 measured runs qualified** under the unchanged v2 audit: **720 case outcomes**, **390 decoded failure PNGs** and **90 native WebMCP setup calls**. Every run kept 11 expected passes, 13 expected failures and all six known defect groups.

## Where the gain came from

| Control | Workers | Median | Range | CPU per run | Qualified | Isolates |
|---|---:|---:|---:|---:|---:|---|
| v2 WebMCP suite on the new browser path | 4 | 4.338s | 3.695–5.168s | 14.5s | 5/5 | Browser build, switches and compile cache |
| e2e only, identical v3 structure, UI fixture setup | 4 | 3.667s | 3.569–3.916s | 15.0s | 5/5 | WebMCP's own share |

- Of the 7.82s saved, the browser path accounts for **6.88s (88%)**. Starting e2e while the browsers boot, plus one browser per worker, accounts for **0.94s (12%)**.
- WebMCP setup itself saved **0.27s (7.4%)** against the identical structure with UI setup. It was faster in **13 of 15** adjacent same-round pairs across the three passes. This fixture replaces only three records per viewport with tools, so WebMCP's own share stays small; e2e only can adopt the rest of the v3 structure and reach 3.667s.

## Implemented changes

1. **Use Playwright's headless Chromium build and automation switches.** It is the same Chromium 156.0.8078.4, and native WebMCP works there. In a three-round pilot on the v2 suite, the run fell from 10.368s to 3.710s, and CPU from 33.81 to 14.35 CPU-seconds. The switch list alone took the headless build from 4.295s to 3.710s, and browser readiness from about 360–410ms to about 105ms. This is the browser e2e's ordinary local target already gets. e2e's own automatic install fetches only this build, so the old full-Chromium launcher could fail where only it is installed. The launcher keeps Chromium's sandbox on. It falls back to full Chromium if Playwright's internal registry lookup moves; `HONEY_WEBMCP_HEADLESS=new` forces full Chromium.
2. **Start e2e while the browsers boot.** e2e needs about 0.4s to load before it asks for a browser. The launcher now spawns it first, and the config's `webmcpBrowsers` provider waits for each Chromium port file. Pilot, five rounds: 3.639s → 3.392s.
3. **Give each worker its own browser.** A verified probe showed that a Playwright CDP client adopts pages another client opens in its own context. On one shared browser, each of four workers therefore also instrumented the other workers' pages. `webmcpBrowsers` uses e2e's browser-provider API, the engine's supported per-worker browser seam, and the launcher starts one browser per `--workers`. Pilot, four rounds: one shared browser 3.411s, four browsers 3.244s.
4. **Enable Node's compile cache for e2e and its workers.** Pilot, five rounds: 3.772s → 3.620s. The cache is warm after the first run, and the warm-up round is excluded, so a first cold run does not get this saving. `NODE_DISABLE_COMPILE_CACHE=1` opts out.
5. **Open no startup page per browser.** `--no-startup-window` matches Playwright's own launches; each test still opens its page in a fresh context. In a four-round pilot with four browsers, every run was faster: 2.986–3.002s became 2.889–2.931s.

An independent review then hardened the launcher without touching the timed path. Repeated Ctrl+C, SIGTERM and SIGHUP are forwarded so e2e can escalate its own teardown, and the launcher stays alive to delete its profiles. A profile that cannot be deleted is retried, then reported without changing e2e's exit code. Without `--workers`, the browser count follows e2e's own worker default. e2e and the engine's pinned Playwright are found through module resolution, so hoisted workspaces work. The provider retries a port file Windows still has open and logs when worker slots must share a browser. The documented config adds the WebMCP target only under the launcher, so a plain `npx e2e run` still runs the other targets. Six cooled rounds of these final files gave a 3.207s median (3.058–3.610s, 6/6 qualified) against 3.531s for the same-structure UI-setup control, with WebMCP faster in 5 of 6 pairs.

Nothing else changed relative to the v2 flow: app behavior, test cases, assertions, timeouts (1000ms assertions, 2000ms actions), retries, four workers, the two-file grouping, the Chromium version and every acceptance UI action are the same. v3's test files are byte-identical to the v2 flow; only the config's browser source and the launcher invocation changed.

Tried and rejected: an uncapped frame rate was slower (3.952s against 3.772s) and used more CPU. More workers did not help on this 8-core laptop: six workers took 3.141s against 3.077s for four, and eight took 3.660s. A Playwright-managed launch would keep a second CDP client on every browser and bring the page adoption back. e2e's in-process runner API would save roughly 60–85ms of boot, but the shipped launcher would lose the e2e CLI interface.

## Measurement protocol

- Same fixture, cases, viewports and seeded defects. The audit function is byte-identical to v2's. It requires the specific priority, persistence, completion, Escape, whitespace-validation and mobile-overflow witnesses, decoded failure PNGs, native failure-screen text for e2e modes, two native discoveries and six setup calls for WebMCP modes, and exit 1.
- One excluded warm-up, then five measured rounds. Mode order rotates cyclically by round, which keeps the UI-setup control immediately before v3 WebMCP. Commands run one at a time. The final pass adds an untimed 8s cool-down before each command.
- Timing covers browser startup, launcher and runner processes, tests, native and normalized report writing, and browser cleanup. Pre-run and post-run time come from e2e's own timestamps. Artifact copying and the audit are outside the timer.
- Three full passes ran; the tables use the final one. Pass 1 had outside load in its last two rounds. Pass 2 started a minute later and ran hot: CPU-seconds per run were about 30% higher and the 1-minute load reached 17.8 on eight cores. One v2-launcher run failed its audit under that load (C01 at both viewports, plus the C11 mobile witness). The v3/v2 ratio was 0.302, 0.334 and 0.303 across the passes. v3/older QA was 0.434, 0.598 and 0.471, because parallel workflows lose more under contention than serial older QA.
- Machine: MacBook Pro 13" with Apple M1 (four performance and four efficiency cores) and 8 GB, Darwin 27.0.0, with about 0.9 cores of other desktop apps active. Node 24.18.0; e2e 0.22.0, @e2e-dev/web 0.15.4 and playwright-core 1.64.1, the latest on npm today; Chromium 156.0.8078.4 for both builds. Upstream e2e main is unchanged at `1d671f6786b1eff4b43718ddc413b0bfa21abbcb`.
- The v2 WebMCP configuration took 9.968s in the v2 report and 11.215s today. Absolute times move with machine state, so every claim here uses ratios from the same rotation.
- Older QA stays serial; e2e modes use four workers, and the v3 launcher starts four browsers. This is a workflow comparison with disclosed resources, not a same-worker engine benchmark.
- This measures prepared test execution. AI reading, first-time authoring, dependencies and server startup are excluded. It does not establish a universal speedup on a production app or a faster cold-agent task.

## Where the remaining 3.4s goes

The v3 median splits into 0.59s before e2e's run starts, 2.72s of run and 0.07s after it. The pre-run time covers three Node starts, the e2e CLI and config load, and the browser leases. Inside the run, workers attach after 0.34s, then each unit runs six tests at a median 356ms each. In a test, opening the app takes a median 76ms, a tap 62ms, a visibility assertion 37ms and a check 79ms. A failed case adds roughly 80–130ms of native failure evidence. Going much lower now means fewer acceptance steps or engine changes, which this pass deliberately did not make.

They cover e2e starting while the browser boots, one isolated browser per worker, the e2e worker default, headless-build selection and its fallback, a stopped run when a browser fails to start, cleanup after repeated interrupts, an undeletable profile keeping e2e's exit code, prompt exit, a preserved failing status and forced cleanup, plus provider lease spreading, port waiting, abort and the missing-launcher error.
