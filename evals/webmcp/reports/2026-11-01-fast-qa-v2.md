The improved WebMCP flow used **27.4% less median wall time than older QA** with the fixed launcher shared by both. The previous WebMCP test flow, measured in the same rotation with that launcher, took **10.710s**; the new flow median was **6.9% lower**. That previous control qualified in 4/5 runs and produced 1 false alarm, so it is not a clean equal-outcome timing control.

Every mode ran five measured repetitions after one excluded warm-up. **19/20 runs qualified** under the full witness/coverage/evidence audit. All **480 case outcomes** and **261 decoded failure PNGs** remain archived, including any unexpected failures. Each WebMCP run records native discovery at both viewports and six setup calls.

## Implemented changes

1. **Cancel the losing shutdown timer.** `Promise.race` does not cancel the timer it races. The launcher previously finished cleanup about 1.963s before Node exited; regression tests independently measured about 2.008s of idle exit delay. The template now aborts the timer after Chrome exits, while retaining the 2s forced-kill deadline for an unresponsive owned browser. This improvement benefits every workflow using that launcher.
2. **Use the assertion that matches the contract.** The checkbox case asks whether the control becomes unchecked. e2e `not.toBeChecked()` additionally requires up to a 1s stability window. `toBeChecked({ checked: false })` retains asynchronous state polling without asking for that extra temporal guarantee. A requirement to remain absent/unchecked still needs the stability check.
3. **Use a direct accessible name.** Checkbox actions now locate the exact `Complete Plan sprint` control rather than repeatedly traversing a filtered row. Other row assertions stay where they prove separate behavior.
4. **Avoid capturing the failure tree twice.** e2e already keeps a semantic screen and PNG on failure. The test no longer asks for another generic tree in `finally`; specific measured values and page errors remain.
5. **Balance the same cases into two files.** Two coherent test files × two viewports supply four worker units. This avoided extra worker startups while retaining one isolated context per test, four workers, identical assertion/action timeout settings and all 24 outcomes. The two-file pilot beat the four-file pilot in both paired trials.

No app behavior, defect expectation, native tool definition, browser version, retry count or acceptance UI action was changed. The routine form, checkbox, search, Escape, validation and responsive checks still use the UI. WebMCP still replaces only eligible fixture creation.

## Measurement protocol

- All modes use the same fixed launcher, machine, server, Chromium 156.0.8078.4 and Node 24.18.0. e2e is 0.22.0, web engine 0.15.4, Playwright core 1.64.1. Upstream main was checked with `gh`; its SHA remains `1d671f6786b1eff4b43718ddc413b0bfa21abbcb`.
- Commands execute sequentially, without simultaneous benchmark runs. The four variants rotate positions by round. The fourth variant is the previous WebMCP flow, retained as a before/after control.
- Timing covers isolated browser startup, runner process, tests, native/normalized report writing and owned-browser cleanup. Artifact copying and the independent witness/PNG audit are outside the timer.
- Twelve behaviors run at 1440×900 and 390×844. Existing scripts retain their data strings and their navigation handling; both use 1000ms assertion timeouts and 2000ms action bounds where applicable. No timeout was shortened for the new flow.
- Older QA remains serial; e2e modes use four workers. This is a workflow comparison with disclosed resources, not a same-worker engine benchmark.
- Failures are expected because the fixture contains six deliberate defects. The audit verifies specific observed values for priority, task persistence, completion persistence, Escape, whitespace validation and mobile overflow, rather than accepting a matching failure count.
- This measures prepared test execution. AI reading, first-time authoring, dependencies and server startup are excluded. It does not establish universal speedup on a production app or a faster cold-agent task. The historical 75–128s agent timings remain a different, unremeasured metric.
